# Applying the 2026-08-21 migrations

Four findings from the functional audit are database drift, not code: they are
fixed by reconciling production with this repo. This is the order to do it in
and how to confirm it worked.

**Take a backup first.** Supabase Dashboard → Database → Backups. Every step
below is wrapped in a transaction, so a failure rolls back rather than leaving
a half-applied state — but a backup is still the thing that saves you.

---

## Why the order matters

The five payout RPCs in production are `SECURITY DEFINER` with **no
authorization of any kind**. During the audit a creator and a client each
reached the final statement of `approve_withdrawal_request` on a real pending
withdrawal — meaning the status check, the `UPDATE … SET status='approved'` and
the `INSERT INTO payments` had already run on their behalf.

They failed only because the deployed function bodies are stale and write to
`payment_audit_logs.performed_by`, a column that no longer exists.

> **That bug is currently the only thing preventing a creator from approving
> their own payout.**

`20260530000001_payout_rpc_functions.sql` has been sitting in this repo
unapplied. It repairs those bodies. Applying it **on its own removes the
accidental brake and leaves the door open.**

`20260821000000` adds the authorization layer. It must land in the same session.
It contains a guard that hard-fails if the bodies are still stale, so the unsafe
order cannot be applied by accident — but the guard cannot stop you from
applying step 1 and then walking away. Do both.

---

## Order

Run these in the Supabase SQL editor, in this order, in one sitting.

| # | File | What it does |
|---|------|--------------|
| 1 | `20260530000001_payout_rpc_functions.sql` | Repairs the five RPC bodies (`performed_by` → `actor_user_id`). **Already in the repo, never applied.** Leaves the authorization hole open — do not stop here. |
| 2 | `20260821000000_payout_drift_and_authz.sql` | Fixes the `creator_earnings` status CHECK (N-03), adds the permission helper, rebuilds `request_creator_withdrawal` with an ownership check and a row lock, seals the other four behind guarded wrappers, and revokes `PUBLIC`/`anon` execute (N-11, F-2, F-8, F-9). |
| 3 | `20260530000002_stripe_connect.sql` | Adds the `stripe_*` columns. **Already in the repo, never applied.** Until this runs, Stripe onboarding returns a misleading "Creator not found" (N-08). |
| 4 | `20260821000001_client_creator_visibility.sql` | Adds the scoped policy that lets a client resolve creator names for work delivered to them, so the content gallery and analytics stop being empty (N-09, F-6). |
| 5 | `VERIFY_20260821.sql` | Read-only. Writes nothing. Every row should report `PASS`. |

## These have been run against a real engine

`__tests__/migration.test.cjs` applies steps 2 and 4 to PostgreSQL 18 (PGlite, the
real engine compiled to WASM) on a fixture schema built from the live production
column lists. **22 checks, 0 failures.** It is what validates the PL/pgSQL bodies —
a plain SQL parse only checks the outer grammar and treats `$$...$$` as opaque text.

```
npm i -D @electric-sql/pglite
node supabase/migrations/__tests__/migration.test.cjs
```

What it proves, beyond 'the SQL is valid':

- A **creator cannot approve their own withdrawal**, a **client cannot approve
  one**, and a **creator cannot mark a batch paid** — each refused with
  `Not authorized`. An owner can.
- A creator who passes the *owner's* UUID as the actor is **still refused**, and
  the audit row records `auth.uid()` rather than the id supplied by the caller.
- A creator **cannot request a withdrawal against another creator's id**.
- `anon` cannot execute any of the five payout RPCs.
- The ordering guard **fires** on stale bodies, and the transaction **rolls back
  with nothing half-applied**.
- Re-running the migration is a no-op rather than an error.

The one check that reports FAIL in the harness is `8. stripe columns present`,
which is correct — the fixture deliberately omits step 3.

## The one thing these migrations do *not* fix

**N-10 — Account Managers can read across tenant boundaries.**

An AM with zero assigned clients saw all ten in production, including another
AM's. Both relevant policies in `20260521000000_omnya_hardening.sql`
(`clients_select_scoped` and `clients_modify_owner_or_assigned_am`) correctly
require `am.user_id = auth.uid()`, and `current_user_role()` was confirmed to
return `am`. Those policies alone would return zero rows.

So **production has at least one permissive policy on `clients` that exists in
no migration in this repo.** It could not be identified from outside the
database — PostgREST does not expose `pg_policies`.

`tests/role-boundaries.test.cjs` builds two independent tenants and confirms the
leak is wider than first reported: an AM can read the other tenant's **client,
campaign and submission**. All three repo policies are correctly written and
would return zero rows, so production simply carries more policies than the
repo does. The single-tenant checks could not see this — with one client in
the system, "sees all" and "sees mine" look the same.

Section 6 of `VERIFY_20260821.sql` lists the live policies on `clients`,
`campaigns`, `submissions`, `creators` and `user_profiles`. Compare that output against `20260521000000_omnya_hardening.sql`.
Anything present live but absent from the migration is the leak. Once it is
named, dropping it is a one-line migration — but the drop is not written here,
because guessing at the name of a policy that governs client data access is not
a safe thing to do blind.

## Deployment config, not SQL

Two items need setting in the Vercel project rather than the database:

- **`UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN`** — unset in
  production, so every rate limit in the codebase currently fails open,
  including on login and the payout endpoints. The limiter code is correct and
  complete; it only needs these two values. See `.env.example`.
- **`CRON_SECRET`** — must already be set for `/api/analytics/sync`. The new
  `/api/cron/purge-oauth-states` job added to `vercel.json` uses the same
  secret and the same constant-time check.
