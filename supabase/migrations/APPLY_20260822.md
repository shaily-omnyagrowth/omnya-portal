# Apply runbook — 2026-08-22

Nine migrations, in this order. Several carry guards that abort if a
prerequisite is missing; that is correct behaviour, but it will look like a
failure if you run them out of sequence.

Every file has a matching `.rollback.sql`. Read the header of any rollback
before running it — two of them reopen a security hole on purpose and say so.

Run each in the Supabase SQL editor and **keep the NOTICE output**. For steps 5
and 8 the NOTICE log is the only record of what production actually had.

---

## Before you start

```
ENCRYPTION_KEY            64 hex chars, or nothing below matters
UPSTASH_REDIS_REST_URL    rate limiting is a no-op without it
UPSTASH_REDIS_REST_TOKEN
```

`ENCRYPTION_KEY` is currently the literal placeholder locally. Generate one
with:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

It must be the **same** key everywhere. If it changes later, every stored token
becomes unreadable and every creator has to reconnect.

## The order

| # | File | What it does |
|---|---|---|
| 1 | `20260530000001_payout_rpc_functions.sql` | Payout RPC bodies. Step 3 refuses to run on top of stale versions. |
| 2 | `20260530000002_stripe_connect.sql` | The 12 missing `stripe_*` columns. **Never applied.** |
| 3 | `20260821000000_payout_drift_and_authz.sql` | N-03 and N-11. Unblocks the money path. |
| 4 | `20260604000000_tiktok_integration.sql` | Baselines the three live token tables. |
| 5 | `20260822000002_token_migration.sql` | Retires `creator_tokens`; removes its browser read. |
| 6 | `20260822000003_campaign_creators.sql` | Referential integrity for campaign assignment. |
| 7 | `20260822000004_payout_ledger.sql` | Append-only journal for the money path. |
| 8 | `20260822000005_tenant_policy_reset.sql` | N-10. Rebuilds the policy set on four tables. |
| 9 | `20260822000006_signup_pending_role.sql` | Signup lands in `pending`. |

### Do not apply `20260821000001_client_creator_visibility.sql`

Its `creators` policy selects from `campaigns`, and `campaigns_select_scoped`
selects from `creators`. PostgreSQL refuses the cycle and **every read of
campaigns fails for every role, including the owner** — `SQLSTATE 42P17`.

It is untracked and evidently never applied, which is the only reason
production is up. Step 8 supersedes it and breaks the cycle with a
`SECURITY DEFINER` helper. Reproduced in
`__tests__/tenant-isolation.test.cjs`.

## What to expect, step by step

**Step 2 — Stripe.** Silent. Afterwards `creators` should have 12 `stripe_*`
columns:

```sql
SELECT count(*) FROM information_schema.columns
WHERE table_name = 'creators' AND column_name LIKE 'stripe_%';   -- expect 12
```

**Step 4 — TikTok baseline.** A no-op against production, since all three
tables already exist. It exists so a fresh database can be built and so the
schema is finally in version control.

**Step 5 — token migration.** Expect one NOTICE per dropped policy:

```
NOTICE:  F-3: dropping creator_tokens policy -> creator_tokens_select_self
NOTICE:  F-3: dropping creator_tokens policy -> creator_tokens_delete_self
NOTICE:  F-3: creator_tokens.access_token is now nullable
NOTICE:  F-3: creator_tokens retired. 0 row(s) remain, 0 still hold plaintext.
```

Both token tables are currently **empty in production**, so there is nothing to
back-fill. If that changes, run:

```bash
node scripts/backfill-tokens.js --dry-run   # report only
node scripts/backfill-tokens.js             # encrypt + upsert
node scripts/backfill-tokens.js --scrub     # erase verified plaintext
```

The scrub phase only erases a row it has personally read back and decrypted to
an exact match. Run it as a separate pass, after the app has run against the
new table.

**Step 8 — tenant policy reset.** The important one. Expect a NOTICE naming
every policy it drops:

```
NOTICE:  N-10: dropping policy public.clients -> client_select_own_profile
...
NOTICE:  N-10: dropped N policy/policies across creators, clients, campaigns, submissions, video_analytics
NOTICE:  N-10: policy set rebuilt and verified.
```

**Any name in that list you cannot find in `supabase/migrations/` is
undocumented drift. Write it down** — that list is the only record of it.

The migration refuses to commit if the rebuilt policy count is wrong, rather
than leaving a role locked out or a table open.

**Step 9 — signup.** Watch for this:

```
WARNING: N-20: N other trigger(s) on auth.users listed above.
```

It does **not** drop unknown triggers on `auth.users` — that table is
Supabase-managed and dropping the wrong one breaks password recovery or email
confirmation. If it lists a trigger that also writes `user_profiles`, the two
will fight and you must resolve it by hand.

After this, **new signups cannot use the portal until an owner approves them**
on the Approve Users page. Existing accounts are untouched.

## Verify

```bash
node supabase/migrations/__tests__/new-migrations.test.cjs    # 45 assertions
node supabase/migrations/__tests__/tenant-isolation.test.cjs  # 16 assertions
node supabase/migrations/__tests__/migration.test.cjs         # 22 assertions
```

Those run against PGlite and pass today. The two that matter against **your**
database:

```bash
node tests/role-boundaries.test.cjs      # 17 held / 7 open  ->  expect 24/24
node tests/payout-acceptance.test.cjs    # exit 3 (blocked)  ->  expect exit 0
```

`role-boundaries` going green is the acceptance criterion for N-10 and N-11 in
production. `payout-acceptance` exiting `0` is the first time the payout chain
will have completed end to end.

Also worth running once:

```sql
SELECT * FROM public.payout_ledger_reconcile();   -- drift should be 0 everywhere
```

Non-zero drift means a status was written without passing through the ledger
trigger, which is the one failure the ledger design has to be able to detect.

## If something goes wrong

Roll back in reverse order. Read the header first — the rollbacks for steps 5,
8 and 9 each reopen something deliberately and say so at the top.

For step 8 specifically, a role losing access it should have kept is far more
likely than the fix being wrong. Check what it actually built before reverting
the whole thing:

```sql
SELECT tablename, policyname, cmd FROM pg_policies
WHERE schemaname = 'public'
  AND tablename IN ('creators','clients','campaigns','submissions','video_analytics')
ORDER BY tablename, policyname;
```

Adding one missing policy back is almost always better than reopening the
tenant boundary for everyone.
